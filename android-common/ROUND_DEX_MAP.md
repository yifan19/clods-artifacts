# Per-round target class → original dex mapping

Generated by running `lib/patch_round.py` offline (dex2jar → `CommandLine` → jar2dex) against each
bug's real, vendored APK and every one of its round plans — see `patch_manifest.json` under each
round's workdir for the byte-for-byte source of this table. This is the information the live
JVMTI agent (`ClassFileLoadHook`/`RetransformClasses` style, see `dex_agent/agent_element.cpp`)
needs per round: which class to target, and which of the APK's ~24 split dex files it originally
came from.

**Do not hardcode this across APK rebuilds** — dex-splitting order is a build output, not a
guarantee. Re-run `patch_round.py` (or re-derive from a fresh `patch_manifest.json`) whenever the
base APK changes. The repetition below (many classes landing in `classes20`/`classes21`/`classes2`)
is a property of these 5 bugs being near-identical builds of the same Element Android base APK
(each differing by one reverted PR), not a fixed rule.

verified end-to-end on 2026-07-14: dex2jar → offline instrumentation → jar2dex, 1/1 classes
patched, 0 warnings, in every round.
